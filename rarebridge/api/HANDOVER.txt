HOW THE IMPORTANT PARTS WORK
Load order: graph.json, disorders.json, base bundles, then the overlay. The overlay
only appends. Startup fails with a full list of problems (nothing overwritten) on: a
source alias mapping to two canonical sources, a source redefined with a different
URL/aliases, a node ID reused with a different type, a duplicate edge or assessment
ID, an edge endpoint or source that does not exist, an unknown target disease, a
schema violation, or an email address stored as a contact URL. Same-type node reuse
merges new keys only and is reported in /api/health overlay.merge_notes. A missing
overlay file is not an error.

Search: normalized exact > word prefix > substring > all-token prefix; diseases are
listed first because search enters the disease journey. Exact IDs and aliases are
matched case-insensitively and returned unchanged. A bare DOI (10.1002/...) finds
the DOI source. Disease association for non-disease hits walks the graph but never
through a hub (another disease, ontology term, gene or publication), so a shared GO
term cannot attach every disease to every claim.

Related diseases (overview and graph), two families kept apart:
  recorded: an explicit overlay edge between the two diseases, or a graph path
    disease -studied_in-> study <-framework_used_by- asset -framework_used_by-> study <-studied_in- disease.
    ranking_method "recorded_route"; review_status is source_checked only if every
    edge of at least one route is source_checked.
  candidate: shared HPO/GO/CL/UBERON annotations in the DisMech records, each term
    weighted ln((N+1)/df) over the N diseases of the slice, score = weighted Jaccard.
    ranking_method "idf_weighted_jaccard_shared_annotations_v1". basis_claim_ids are
    the real claim IDs on both sides; source_ids are the DisMech records. Always
    pending; reason text says it establishes no shared mechanism or treatment.
  One entry per related disease; recorded routes first. Each entry also carries that
  community's organizations (additive "organizations").

Opportunities are strictly target-scoped: (asset, target disease, goal). STXBP1
shows framework-for-stxbp1 only. With the overlay off it shows none, and
coverage.gaps says framework-for-syngap1 was not substituted. Assets documented for
the disease but with no scoped bundle appear in additive "unassessed_assets" with
assessment_id null, never in opportunities.

Assessment: before/after are the exact assess() results; nonempty withdrawals call
compare_withdrawal(). DOI and PMID withdraw the same paper. An empty list is the
reset. The stored bundle is deep-copied and never mutated (tested). A source that
exists elsewhere in the slice but is not cited by this assessment is reported in
withdrawn_source_ids_ignored instead of failing, so a global "hide this source"
toggle works across views; a truly unknown ID gives 422.

Contacts: curated overlay contacts first, then the asset record's
public_researcher_routes, matched by name first and by URL only when the URL is
unambiguous. Unmatched routes become derived contacts with review_status pending
and last_checked null. A contact whose every source is withdrawn is flagged
all_sources_withdrawn.

Graph: node groups are added whole in relevance order (query disease, assessment
asset and sources, assessment contacts, related diseases, recorded route, contacts,
related-community organizations, gene associations, key mechanism claims, shared
annotation basis, assets, remaining claims, phenotypes, upstream evidence). Nodes
left without any served edge are dropped. Every edge has provenance, review_status,
source_ids, claim_origin, a qualitative confidence_label and an explanation.
Imported DisMech edges carry the contract pending label ("Unassessed ... source review pending"). Synthetic
edges: assessment_scope and evidence_for_check (from the curated bundle),
listed_as_public_route, candidate_shared_annotations (inferred, pending). No
therapeutic or eligibility relation is ever served (tested). coverage.truncated
means relevant nodes were hidden by max_nodes; omitted_relevant_nodes and
skipped_groups say which.

DIFFERENCES FROM THE FIXTURES (all fixture field paths are present; values differ)
  1. Disease labels come from DisMech: "SYNGAP1-Related Developmental and Epileptic
     Encephalopathy", "STXBP1 Encephalopathy", "SCN2A-Related ...". The fixture's
     "SYNGAP1-related disorder" is still a searchable synonym.
  2. Route-derived researcher contacts are review_status "pending". The fixture said
     "source_checked", but no review-log entry checks authorship.
  3. ranking_method values: "curated_target_scoped_assessment" for opportunities,
     "recorded_route" or the candidate method name for related diseases.
  4. data_origin is "dismech_snapshot" or "dismech_snapshot+curation_overlay", not "mock".
  5. Overlay researcher IDs are researcher:jillian-mckee and researcher:ingo-helbig
     (fixture: researcher:jillian-l.-mckee). The frontend must not hardcode contact IDs.
  6. Additive fields exist on most responses (outcome, open_required_check_ids,
     shared_terms, recorded_routes, coverage.gaps, source_roles, asset_context, ...).
     They are optional; nothing in the contract changed meaning.

KNOWN LIMITATIONS
  - Three diseases. Annotation overlap is sparse: each disease pair shares 4 terms,
    scores about 0.05. SCN2A connects to the others only through these candidates.
  - Search is lexical. No fuzzy matching, no medical vocabulary expansion.
  - No database, no live recruitment or availability check, no multi-user editing.
    Overlay changes need an API restart.
  - The overview runs assess() per opportunity on each request; fine at this size.
  - Graph responses keep upstream_record on nodes (about 75 kB for 40 nodes).
  - The candidate score is a ranking aid, not a probability or clinical confidence.

FOR THE LEAD: AI SERVICE HOOK
Create rarebridge/ai/__init__.py and rarebridge/ai/service.py with:
  async def extract_source(payload: dict) -> dict        # must pass extraction.schema.json
  async def explain_assessment(assessment: dict, sources: dict) -> dict
       -> {generation_mode: "live"|"cached", text, cited_source_ids, model}
  def capabilities() -> dict   # recommended: {"ai_extraction": bool, "ai_explanation": bool},
                               # e.g. False when OPENAI_API_KEY is missing
  class ModelUnavailable(Exception)   # optional; raised -> HTTP 503 model_unavailable
The bridge imports the module on demand (no backend change needed), validates
extraction output against the schema, rejects any extracted claim that is not
"pending" and any explanation citing a source outside the assessment (HTTP 502
ai_output_invalid), and times out with 502 ai_timeout. POST /api/ai/explain
computes the post-withdrawal assessment and passes it with its sources. Extraction
results are returned with import_status "not_imported"; graph import and any
review promotion stay with the lead.
